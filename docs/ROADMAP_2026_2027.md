# Python Learning Dashboard — Roadmap 2026–2027

**Planning window:** 2026-11 to 2027-10  
**Status:** Proposed; dates depend on capacity, audit findings and user feedback.  
**Rule:** Finish and measure each stage before expanding scope.

## Outcomes for the year

1. A reliable and documented core learning journey.
2. A reviewed Python path from first concepts to a final assessment.
3. Evidence that learners can use the product repeatedly and improve.
4. A tested hypothesis for paid individual features.
5. A decision, based on interviews, on whether to pilot academy features.

## Stage 0 — Stabilise (November 2026)

**Goal:** Protect existing functionality, user data and release reliability.

Deliverables:
- Review open PRs and unresolved defects before merging.
- Regression-test login, registration, Google sign-in, recovery, logout and account deletion.
- Test progress sync across devices, tabs, retries and stale local state.
- Review API rate limiting, deployment cold starts, database backups and restoration.
- Complete an accessibility review, including manual keyboard/screen-reader checks.
- Review privacy, terms, licensing and legal readiness; document open questions.
- Capture baseline performance and reliability.

Acceptance criteria:
- No known data-loss defect remains open without a documented mitigation.
- Critical account and sync flows have automated regression tests.
- Release checklist and rollback/recovery procedure are documented.
- Remaining risks have an owner, severity and next action.

## Stage 1 — Cohesive Python learning path (December 2026)

**Goal:** Make the main learner journey clear and complete.

Deliverables:
- Define the target learner, prerequisites and outcomes.
- Review lesson order, explanations, examples, exercises and feedback.
- Run automated validation for every executable example and answer key.
- Add lesson-level completion criteria and a final assessment.
- Ensure navigation, resume behaviour and mobile layout are consistent.
- Verify source, attribution and licence for third-party material.

Acceptance criteria:
- A new user can start, complete a lesson, practise, understand a wrong answer and resume later without assistance.
- All published exercises pass the content checks.
- Known gaps are labelled rather than presented as complete coverage.

## Stage 2 — Learning diagnosis and product instrumentation (January–February 2027)

**Goal:** Recommend useful next actions and collect enough data to improve the product.

Deliverables:
- Establish a versioned content schema and stable IDs.
- Link reviewed exercises to learning objectives.
- Implement baseline rules for recommendations and review scheduling.
- Explain recommendations to the learner in plain language.
- Add privacy-minimised events for activation, attempts, completion and return use.
- Add an internal view or report for aggregate funnel and content-quality metrics.

Acceptance criteria:
- Recommendations are deterministic and testable.
- A learner can see why an activity is recommended.
- Analytics do not collect credentials, full code submissions or unnecessary personal data.
- Events and retention are documented and can be disabled/configured appropriately.

## Stage 3 — Learner validation (March–April 2027)

**Goal:** Determine whether the product is useful before expanding it.

Deliverables:
- Recruit 10–20 voluntary testers, including beginners and DAW students.
- Observe onboarding and first-exercise completion.
- Run a multi-week pilot and collect interviews.
- Compare equivalent pre/post assessments where feasible.
- Track 7-day and 28-day return rates, exercise completion and technical failures.
- Rank issues by frequency and impact.

Acceptance criteria:
- Findings include observed behaviour, not only self-reported satisfaction.
- At least the top five usability/content problems have a prioritised response.
- Product decisions document what evidence supports them and what remains uncertain.
- No paid expansion is approved solely on the basis of traffic or compliments.

## Stage 4 — Paid-plan experiment (May–July 2027)

**Goal:** Test willingness to pay without compromising the free learning path.

Potential paid value to test:
- Advanced learning paths and study plans.
- Expanded practice exams and performance breakdowns.
- Personalised review recommendations.
- Exportable progress reports or project-based learning packs.

Deliverables:
- Interview engaged learners about willingness to pay.
- Select one or two paid benefits, not a broad feature bundle.
- Model provider fees, support, taxes and variable AI costs if applicable.
- Implement billing only after terms, cancellation, refunds, invoices and entitlement handling are reviewed.
- Test the payment and cancellation journey with a small pilot.

Acceptance criteria:
- Pricing and value proposition are tested with real users.
- Payment, entitlement and cancellation state are consistent and auditable.
- The free tier remains useful.
- Unit economics include payment fees, infrastructure, support and acquisition cost assumptions.

## Stage 5 — Decide on B2B academy pilot (August–October 2027)

**Goal:** Establish whether teacher and academy workflows justify a separate product track.

Deliverables:
- Interview teachers and small academies.
- Validate the need for groups, assignments and progress reporting.
- Secure a credible pilot partner before building a broad admin system.
- Define organisation membership, role permissions and data separation.
- Prototype the smallest useful teacher workflow.

Acceptance criteria:
- At least one partner commits to a defined pilot or the B2B track is deferred.
- Access control and data separation have tests.
- The scope is limited to groups, assignments and learner progress unless evidence justifies more.

## Quarterly review gates

At the end of each stage, decide to continue, change direction or stop. Review:
- learner activation and retention,
- evidence of learning improvement,
- content accuracy and defects,
- sync/reliability issues,
- accessibility and privacy risks,
- willingness to pay,
- development and support costs.

Do not set arbitrary growth targets before establishing the baseline. Record actual values and the sample size behind them.

## Work that stays deferred

- Full React rewrite or framework migration.
- Microservices.
- Native mobile apps.
- Full school-management/LMS administration.
- Server-side arbitrary-code execution without a separate isolation project.
- Broad AI tutor features before an evaluation set and cost model exist.
- Expanding every DAW/DAM module before the core path is proven.

## Delivery process

Each roadmap item should become a GitHub issue with:
- user problem and intended outcome,
- scope and explicit non-goals,
- acceptance criteria,
- test and accessibility implications,
- privacy/security implications,
- dependencies and rollback notes.

Use small PRs. Keep the main branch deployable and update this roadmap when evidence changes the sequence.
